# 哼唱转乐器轨 实现方案

## 1. 技术选型与理由

| 环节 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.11 | 音频生态最全（librosa / CREPE / mido / pretty_midi） |
| 界面 | 本地 Web 单页 + 后端 FastAPI | 浏览器录音权限简单、实现最快；后期用 PyInstaller 打成 .app |
| 音高识别 | torchcrepe（CREPE 单音高） | 专为单声部人声/单音乐器设计，对哼唱比通用模型稳。备选 basic-pitch 实测对比 |
| 节奏 | librosa.beat.beat_track 估速 + 网格对齐 | 成熟方案；BPM 允许手动覆盖 |
| 鼓 | librosa onset 检测 + 频谱特征分件 | 无训练成本，规则简单可调 |
| MIDI | pretty_midi / mido | 标准 MIDI 写出，格式稳定 |
| 打包 | PyInstaller → .app | 双击即用，不碰命令行 |

## 2. 模块拆分

1. **录音采集**：前端 MediaRecorder 录 webm/opus → 后端转 wav 16kHz 单声道
2. **预处理**：去静音头尾、归一化、（可选）轻度降噪
3. **旋律分析**：CREPE 出逐帧音高 → 音符分割（按音高稳定段 + 能量门限）→ 音符列表
4. **节奏量化**：估 tempo → 起音对齐网格 → 输出量化后音符
5. **鼓分析**：onset 检测 → 按低频/中频/高频能量分到 kick / snare / hihat
6. **MIDI 生成**：
   - 钢琴 / 吉他：channel 1，program 0 / 24，旋律音高
   - 鼓：channel 10，note 36 kick / 38 snare / 42 hihat
7. **输出存储**：`~/Music/HumToTrack/` 下 `.mid` + 同名 `.json`（原始音符、tempo、参数，便于回溯）。MVP 阶段受沙盒限制，先落在 `mvp/out/`，可用环境变量 `HUM_OUT` 覆盖。
8. **界面**：录音按钮、乐器选择、BPM 输入、结果卡片、Finder 定位

## 3. 数据与接口要点

- 接口：`POST /api/convert`，multipart：`audio`(wav) + `instrument`(piano/guitar/drum) + `bpm`(可选)
- 返回：

```json
{
  "midi_path": "/Users/xxx/Music/HumToTrack/20261117-0930_hum_piano.mid",
  "tempo": 92,
  "duration": 18.4,
  "notes": [{"start": 0.5, "dur": 0.75, "pitch": 60, "velocity": 80}]
}
```

- 文件命名：`YYYYMMDD-HHMM_<instrument>.mid`
- 采样率统一 16kHz 单声道进分析，MIDI 时间以秒计算、量化时按 BPM 转拍

## 4. 里程碑

| 阶段 | 内容 | 预估 |
|---|---|---|
| M1 | CLI 跑通：喂 wav → 出 .mid，拖进库乐队验证能听 | 1~2 天 |
| M2 | 本地 Web UI：录音 → 出文件 | 2~3 天 |
| M3 | 鼓模式（分件） | 1~2 天 |
| M4 | 打包 .app，桌面双击用 | 1 天 |

先验证 M1 的音准/节奏能不能听，再谈界面。M1 不过就不要往下做。

## 5. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| CREPE 对气声、跑调、颤音识别不稳 | 出谱错音 | 限制输入为 8~16 小节短句；加能量门限；与 basic-pitch 对比选优；先跑 10 段真实哼唱测正确率 |
| 无伴奏哼唱自动估 BPM 不准 | 节奏全错 | V1 以手动 BPM 为准（可点节拍器），自动值只做默认 |
| "哒哒"鼓分件误判 | 鼓件错位 | 保底方案：先全部当军鼓/底鼓单一音色，分件作为增强项灰度上 |
| 库乐队无法自动导入 | 多一步手动拖入 | 不承诺自动化，出文件 + 打开 Finder 定位 |
| 浏览器录音格式不统一 | 后端解码失败 | 后端统一 ffmpeg 转码，不依赖前端格式 |
